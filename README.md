# pgen.zig

**Work-in-progress**: This repo is in early stage of development. It currently supports only LR(0) and SLR.

This is an [LR parser generator](https://en.wikipedia.org/wiki/Compiler-compiler) for Zig.

It takes in a plain text file describing a programming language's grammar, then generates a parser (in Zig source code) for it!

A parser takes in a string and turns it into a parse tree for further processing. [LR](https://en.wikipedia.org/wiki/LR_parser) describes a class of parsers. Not all languages can be parsed by LR parsers, but it is sufficient for most programming languages (plus, there are ways to "dig holes" in the parser so that it can do more than what an LR parser in the strict sense can do). Currently only the LR(0) and SLR variants of LR family parsers are implemented (the simplest ones :) but LR(1)/LALR will be added in the future.

## Using this for your project

You can try out by [building](#building) the CLI. Basic usage:

```sh
pgenzig -o out_file.zig in_file.txt
```

Use `pgenzig -h` to see full usage.

To integrate pgen.zig into your Zig Build System, add pgen.zig to your build.zig.zon file using:

```sh
zig fetch --save=pgen git+https://github.com/CBerJun/pgen.zig
```

Then, update your build.zig with something like:

```zig
// The parser generator must target host architecture.
const pgen = b.dependency("pgen", .{
    .target = b.graph.host,
    .optimize = optimize,
});
const pgen_cli = pgen.artifact("pgenzig");
const run_pgen = b.addRunArtifact(pgen_cli);
run_pgen.addFileArg(b.path("src/my_input_grammar.txt"));
const parser_src = run_pgen.addOutputFileArg("parser.zig");
// The generated parser should target the actual build target.
const parser_mod = b.createModule(.{
    .root_source_file = parser_src,
    .target = target,
    .optimize = optimize,
});
// Now you can add `parser_mod` as a dependency just like other Zig modules.
const exe = b.addExecutable(.{
    .name = "my_program",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
        .imports = &.{
            // Import the parser using `@import("parser")`.
            .{ .name = "parser", .module = parser_mod },
        },
    }),
});
```

pgen.zig will be run at build time, but your application will only contain code generated by pgen.zig, not pgen.zig itself. If your grammar contains a mistake it will fail at build time.

See `examples/` for example projects using pgen.zig.

## Building

Just do `zig build`. Current Zig version is 0.16 (will be ported to higher version soon).

The input of pgen.zig (which describes a language) is itself a language! So pgen.zig uses itself to parse its own input. Of course, there is a chicken-and-egg problem here so the first parser used to bootstrap pgen.zig was derived from a hand-translation of the grammar into pgen.zig's own internal representation (a CFG object consisting of a `SymbolSpec` and a `CfgProductions`, representing an already-parsed [context-free grammar](https://en.wikipedia.org/wiki/Context-free_grammar)). Despite calling it "hand-translation", the CFG was actually emitted by `src/bootstrap/generate_meta_cfg.zig` during the build process. Then `src/bootstrap/generate_meta_parser.zig` generates the parser from the generated CFG and a selected subset of the pgen.zig library (the "core"). The generated parser is then combined with the core to form the final pgen.zig library. `build.zig` handles all this mess automatically, so that no precompiled binary is needed to bootstrap pgen.zig.

### The Web Demo

The Web Demo allows you to try pgen.zig in browser. It will generate a parser (in Zig source code) for you. But that's mainly for preview only since you'll need to have a Zig compiler and write downstream code to actually use the generated code.

To build the in-browser demo you need Python (3.10+). Just run `demo/build.py` from the repo root, and the built website is in `demo/dist`. You can then use any HTTP server you like to serve the contents in it. Since we're already using Python, you can do `python -m http.server -d demo/dist` then navigate to `localhost:8000` in your browser to view the demo.

## Technical documentation

As a parser generator, pgen.zig reads in a stream of *tokens* and emits a *parse tree* (*concrete syntax tree*, or *CST* in short). For instance, if your're making a programming language then each identifier (e.g. `foo`, `variable_name`, `functionName`), keyword, literal (`"string"` or `42`), and punctuation (e.g. `+`, `-`, `.`, `>=`) can be considered a token. Tokens are the smallest unit your grammar can handle, and it's up to you to define what kinds of tokens to use. All tokens have a *tag* which indicates its kind (e.g. keyword/number/string/...). The CST has a tree structure, and it's easier to see an example than explaining it with words.

### The grammar file

pgen.zig takes in a plain text ASCII file and emits a Zig source file for it. The plain text specifies the grammar. It follows the following format:

```text
tokens {
    NAMED_TOKEN1;
    NAMED_TOKEN2;
    "";  # Literal token with an empty suffix
    ""sym;  # Literal token with "sym" as suffix
}

entry entry_nonterminal;

entry_nonterminal:
    # ... <right hand side>
    ;
# ... <more rules>
```

The `tokens` section declares all the token tags you will use. Each declaration ends with a semicolon. You may specify an identifier for a *named token* or use an empty string (with an optional suffix) for a *literal token*. Named tokens have a named tag and will be referred to directly using that name; literal tokens have tags identified by a string with a suffix (which can be empty). For instance, `NAMED`, `"wow"`, `"WOW"`, `"wow"sym`, `"+"sym` are all different tokens given the above `tokens` section. A literal token declaration in the `tokens` section merely declares the existence of that suffix. The compiler automatically collects all the literal tokens that have appeared in the grammar, so you don't need to declare them one by one. You simply declare the suffix.

The rest of the grammar consists of definitions of *nonterminals*, and a single nonterminal that is marked as the *entry*. A *nonterminal* can be thought of as a component in your desired language. For instance, in a programming language you could have an `expr` nonterminal which indicates any expression, then you can reuse that `expr` component in many places, like the condition for an `if` statement, or the return value in a `return` statement. In fact, the entire language must in the end boil down to a single nonterminal, and that's the entry. For each nonterminal, you must specify its rule: what it can "expand" to. For instance, an `expr` can expand to `42` (a single number token), `20 + 40` (a number token followed by a plus punctuation followed by a number token), or `functionCall(10, 20)`, but not `return 30;` (a statement), `++` (invalid expression), or something else.

To specify the expansion rule for a nonterminal, you can use a syntax similar to regular expressions (as a convention we'll use uppercase for token names and lowercase for nonterminal names, and `##`/`@@` will denote another full expression):

* `x: A` means nonterminal `x` must expand to exactly the token `A`.
* `x: y` means nonterminal `x` must expand to another nonterminal `y`.
* `x: A b C` means nonterminal `x` must expand to token `A` followed by nonterminal `b`, then followed by token `C`.
* `x: ## | @@` means nonterminal `x` must expand to either `##` or `@@`.
* `x: (##)` means the same as `x: ##`.
* `x: epsilon` means nonterminal `x` must expand to nothing.

Now you can combine these to express many things:

* `x: x ## | epsilon` means `x` must expand to zero or more `##`.
  * pgen.zig provides `x: ##*` which is easier to read.
* `x: x ## | ##` means `x` must expand to one or more `##`.
  * pgen.zig provides `x: ##+` which is easier to read.
* `x: ## | epsilon` means `x` must expand to either nothing or `##`.
  * pgen.zig provides `x: [##]` which is easier to read.

Now, to specify the rule for a nonterminal, you can use `nonterminal_name: ##;`. The `entry` declaration must come immediately after the `tokens` section.

For some examples, you can check out [examples/calculator's grammar](examples/calculator/src/grammar.txt), or [pgen.zig grammar format's own grammar (the meta grammar)](src/bootstrap/meta_grammar.txt). The precedence rule of the operators can also be found out in the meta grammar.
